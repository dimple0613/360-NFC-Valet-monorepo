  **Real gotchas hit and fixed, in the order they surfaced:**

  1. Every deployment (git-triggered and direct CLI `vercel deploy` alike) was silently stuck `BLOCKED` with "commit author does not have contributing access to the project on Vercel." Disabling the project's `gitForkProtection` setting via the API did *not* actually fix it (confirmed: identical block persisted on the next attempt) — the real, only-working fix was deploying from a git-free source snapshot (`git archive HEAD | tar -x` into a scratch directory, `vercel link` + `vercel deploy --prod` from there) so there was no commit-author metadata for Vercel to evaluate at all. Root cause for *future* git-triggered deploys: this repo's local git identity (`technosarjan`) didn't match the Vercel team owner's GitHub identity (`strats360`) — fixed by setting `git config user.name`/`user.email` for this repo to match the account that owns the Vercel team, so normal `git push`-triggered deploys stop hitting this block going forward. A blocked deployment can't be retried in place ("try again from a fresh commit" — confirmed via `vercel redeploy` erroring), and an empty commit gets auto-canceled by Vercel's own change-detection ("project was not affected") rather than forcing a rebuild, so a real file change is required to trigger a fresh attempt after a fix like this.

Once deployments actually ran, `/api/v1/*` routes 500'd with `PrismaClientInitializationError: could not locate the Query Engine for runtime "rhel-openssl-3.0.x"` (confirmed via the Vercel dashboard's runtime logs — the CLI's own `vercel logs` never returned anything useful in this environment). Still not sufficient on its own.
     - Even with the binary correctly bundled, Prisma's own runtime search for it (a fixed set of guessed root/subpath combinations, visible in the error's own "the following locations have been searched" list) never happened to match this monorepo's actual layout. Fixed with an explicit `PRISMA_QUERY_ENGINE_LIBRARY` override in `packages/db/src/client.ts`, computed by checking a few real candidate paths at startup and only running on Linux (local dev's default search already works fine on Windows, untouched).

## Phase 1A — Multi-tenancy & platform foundation

- [x] Prisma schema: `Organization`, `Team`, `Workspace` models with nesting (FR-106) — also added the `User` model and `OrganizationMembership`/`TeamMembership`/`WorkspaceMembership` join tables it depends on (multi-org membership per FR-105). Teams nest via self-relation (`parentTeamId`); Workspaces belong to an Org and optionally a Team. Migration `20260810075705_init_organization_team_workspace` applied to local Postgres; all `organizationId`/`teamId`/`workspaceId` FK columns indexed per NFR-9. RBAC (Role/Permission) and the tenant-scoping enforcement layer are still separate, unstarted tasks below.
- [x] Automatic tenant-scoping layer: Prisma Client extension (`packages/db/src/tenant-scoping.ts`) applied to every tenant-scoped model (originally including `Team`, `TeamMembership`, `Workspace`, `WorkspaceMembership` — see the removal note below; `OrganizationMembership` and others remain) — reads/writes/upserts/deletes all get `organizationId` injected from an `AsyncLocalStorage`-based context (`packages/db/src/tenant-context.ts`), fail-closed (`MissingTenantContextError`) if no tenant context is active. Escape hatch (`unsafeRunWithoutTenantScoping`) reserved for the Super Admin portal/maintenance scripts. Regression tests in `packages/db/src/__tests__/tenant-scoping.test.ts` cover: no-filter reads staying tenant-bound, cross-tenant findUnique/update/delete all no-op instead of leaking or mutating, create ignoring a spoofed `organizationId`, the fail-closed error, and the explicit bypass. CI (`ci.yml`) now runs a real Postgres service + `prisma migrate deploy` before tests so this suite runs there too. **Known gap:** nested relational writes aren't covered by the extension yet — avoid them on these models until it grows that support.
- [x] **Team/Workspace removed (post-Phase-1, retroactive simplification).** The nested `Team`/`Workspace` sub-structure built above was deliberately dropped after a requirements brainstorm concluded it was unnecessary complexity, not a real product need — organization membership is now flat (a user belongs directly to an org via `OrganizationMembership`, per amended FR-106). Real removal, not a deferral: migration `remove_team_workspace` drops `teams`/`team_memberships`/`workspaces`/`workspace_memberships` and `resource_usage_events.workspaceId`; `tenant-scoping.ts`'s scoped-model list, `core-permissions.ts` (`core.teams.read`/`core.teams.manage`/`core.workspaces.manage` retired, including the already-seeded `Permission` rows), `resource-consumption.ts`'s `workspaceId` param, `organization-lifecycle.ts`'s `exportOrganizationData`, the `/tenant-admin/teams` page, and the `GET /api/v1/teams` route (and its `openapi.yaml` entry) were all updated/removed to match. REQUIREMENTS.md (FR-106, FR-121, FR-154, FR-170, FR-173) and ROADMAP.md amended to reflect the flat model as the actual spec, not just a code change out of sync with it.
- [x] Tenant context resolver: middleware for web (session → current org) and API (header/token → org scope) (FR-103). `web/src/lib/tenant/resolve-tenant.ts` has pure, unit-tested resolution logic (7 tests) — `resolveOrganizationIdFromHeaders` (API, reads `X-Organization-Id`) and `resolveOrganizationIdFromCookieValue` (web, reads an `active_org_id` cookie). Thin Next.js glue wraps them: `withApiTenantContext` (`api.ts`) for `app/api/**/route.ts` handlers, `withWebTenantContext` (`web.ts`) for Server Components/Actions — both call `runWithTenant` from `@saasclaude/db`. **Known placeholder, revisit in Phase 1B:** the web cookie is read directly with no session store behind it yet (any value in `active_org_id` is trusted as-is), and the API header is trusted with no token verification. Both are named/structured so swapping in real session/token lookups later doesn't change call sites, but until then neither is actually secure — don't expose real routes through these wrappers before Phase 1B auth lands.
- [x] Cross-tenant access handling: return 404 (not 403), write to audit log (FR-104). Built together with the "Audit log service" item below since FR-104 needs a real place to write to — see that entry for the `AuditLog` model. `packages/db/src/cross-tenant.ts`'s `auditIfCrossTenantAttempt` distinguishes a genuine not-found (id exists nowhere) from an actual cross-tenant reach (id exists, just in another org) by re-checking unscoped only after the tenant-scoped lookup came back empty, and only audit-logs the latter — logged against the *actor's* own org, not the target org whose resource was reached for. `web/src/lib/tenant/not-found.ts`'s `resourceNotFound` wraps this into a 404 `NextResponse` for route handlers. 2 regression tests confirm the not-logged/logged split. No real route wires this in yet (Super/Tenant Admin portal shells are still unbuilt) — it's ready for when they land.
- [x] Organization lifecycle service: create/suspend/reactivate/archive/delete-with-grace-period + soft-delete/export path (FR-132). Built together with the event bus below since FR-133 requires lifecycle actions to publish on it. `packages/db/src/organization-lifecycle.ts`: `createOrganization`/`suspendOrganization`/`reactivateOrganization`/`archiveOrganization`/`scheduleOrganizationDeletion`/`cancelScheduledDeletion`/`exportOrganizationData`/`executeDueOrganizationDeletions`. State transitions go through an atomic `updateMany` compare-and-set (`status IN (...allowed)`) rather than read-then-write, so concurrent calls can't race into an invalid state; invalid transitions throw `InvalidOrganizationTransitionError`, unknown ids throw `OrganizationNotFoundError`. Schema change: swapped the never-used `deletedAt` for `deletionScheduledFor DateTime?` (migration `20260810093844_org_deletion_scheduling`) — a hard-deleted org's row is actually gone, so the historical record of that lives in the audit log (`organization.deleted`), not a marker column with nothing left to mark. `exportOrganizationData` is real but intentionally not GDPR-complete yet — it bundles what Phase 1A actually models (teams, workspaces, roles, memberships), and grows as more tenant-scoped models are added. `executeDueOrganizationDeletions` (hard-deletes past-grace-period orgs) is fully implemented and tested but **not wired to any scheduler** — there's no scheduled-jobs infra yet; call it from whatever cron/queue mechanism lands later. 8 regression tests cover the full state machine, audit trail, event emission, export, and grace-period deletion.
- [x] Domain event bus (in-process pub/sub to start) + publish org lifecycle events (FR-133). `packages/db/src/event-bus.ts`: minimal `on`/`emit`, in-process, process-wide singleton (same hot-reload guard pattern as the Prisma client). Event payloads are plain serializable objects carrying `organizationId` explicitly (FR-102 lists domain events among things that must be tenant-scoped) — a handler needing DB access is responsible for its own `runWithTenant(...)`, the bus doesn't do that for you. `emit` awaits handlers sequentially and propagates a handler's throw to the caller (not fire-and-forget) — callers that want lifecycle actions to succeed regardless of listener failures need to catch around their own `emit` call themselves. Covered indirectly by the lifecycle service's tests (asserting `organization.created` fires with the right payload); no dedicated bus-only test since the mechanism is a handful of lines and the interesting behavior (does a real lifecycle action actually emit correctly) is what's tested.
- [x] RBAC schema: `Role`, `Permission`, `RolePermission`, `UserRole` — roles as data, platform vs tenant role tables kept distinct (FR-113, FR-150). `Permission` is a global catalog (`scope: PLATFORM | TENANT`) shared by both role systems. Platform side (`PlatformRole`/`PlatformRolePermission`/`PlatformUserRole`) has no `organizationId` anywhere — entirely separate from tenant `Role`/`RolePermission`/`UserRole`, which are org-scoped (`Role.organizationId`, denormalized onto the two join tables) and were added to the tenant-scoping extension's model list. Migration `20260810090427_rbac_schema`. 3 new regression tests confirm `Role` gets the same cross-tenant isolation as the Phase 1A models, and that `Permission`/`PlatformRole` work with no tenant context (as they must, being global). Permission↔role-system scope matching (a `TENANT`-scope permission can't end up on a `PlatformRole`) is a service-layer invariant, not a DB constraint — enforced once the permission registry service (next item) exists.
- [x] Permission registry service (modules register permissions at "install" — Phase 1 has one registrant: core itself) (FR-152). `packages/db/src/permission-registry.ts`'s `registerPermissions()` idempotently upserts a module's permission definitions into the `Permission` catalog by key, and throws `PermissionKeyConflictError` if a different module tries to claim an existing key. `packages/db/src/core-permissions.ts` is core's own manifest (8 permissions covering what Phase 1A actually models: org/team/workspace/role management, platform-level org lifecycle + impersonation) — deliberately not exhaustive, grows as the authorization policy layer (FR-153, still unstarted) and real endpoints are built. Wired as a runnable seed: `pnpm --filter @saasclaude/db run seed` (uses `tsx`, configured as `prisma.seed` too so `prisma db seed` works). CI now runs this seed step after migrations. 3 regression tests cover create/idempotent-update/conflict.
- [x] Authorization policy layer enforced server-side on every mutating endpoint (FR-153). `packages/db/src/authorization.ts`: `userHasOrganizationPermission`/`requireOrganizationPermission` resolve a user's permission keys via `UserRole → Role → RolePermission → Permission` (explicitly re-checks `role.organizationId` too, not just trusting the UserRole row's own extension-enforced `organizationId`, in case one ever pointed at a foreign-org role). `getUserOrganizationPermissions` returns the same permission-key set a UI would need — the single source both a server check and UI visibility should read from, per FR-153's "never a separate, divergent UI-only check." Platform equivalents (`userHasPlatformPermission`/`requirePlatformPermission`/`getUserPlatformPermissions`) go through the raw client, no org scoping applicable. `requireOrganizationPermission`/`requirePlatformPermission` both take an optional `condition` closure, evaluated only after the base permission check passes — the FR-154 ABAC hook (ownership, workspace membership, etc.), deliberately left as a plain predicate rather than a full attribute-matching DSL since nothing today needs more. **Scope decision:** no Next.js route wiring yet, unlike the tenant-context resolver — that resolver could reasonably use a placeholder header/cookie, but faking *identity* the same way for permission checks would normalize an actually-insecure pattern, so these functions take `userId` as an explicit trusted parameter and wait for Phase 1B auth to supply one for real. 8 regression tests cover grant/no-grant, cross-org isolation, the ABAC condition, and both role systems.
- [x] Settings service: `Setting` model with scope (platform/org/user) + inheritance/override resolution, encryption for sensitive values (FR-270, FR-271). Three separate models (`PlatformSetting`, `OrganizationSetting`, `UserSetting`), not one polymorphic table with a nullable organizationId/userId — matches the PlatformRole/Role split already in this codebase, and sidesteps a real Postgres gotcha: a unique constraint on a nullable column treats every `NULL` as distinct, which would've silently broken "one platform-scope row per key." `category` is a free-form string, not FR-270's category list as an enum, so a module registering its own settings (FR-272, unstarted) won't need a core change. `OrganizationSetting` was added to the tenant-scoping extension's model list; `PlatformSetting`/`UserSetting` are deliberately not (no single org owns a platform-wide or cross-org personal setting). Migration `20260810094956_settings`. Encryption (`packages/db/src/encryption.ts`): AES-256-GCM, per-value random IV, key from `ENCRYPTION_KEY` (added to `.env.example`, `packages/db/.env`, and CI's env block; generalized from `SETTINGS_ENCRYPTION_KEY` once Phase 1B needed the same primitive for MFA secrets) — sensitive values are ciphertext in the same `value` column plaintext JSON uses. `resolveSetting()` implements the inheritance/override rule: user setting > organization setting > platform default, most specific wins. `list*Settings()` functions redact sensitive values (`"[REDACTED]"`) rather than decrypting them for display — encrypting at rest would be pointless if every listing call handed the plaintext back out. 10 regression tests cover round-tripping, per-org/per-user isolation, upsert-not-duplicate, encryption (including that ciphertext actually differs from plaintext and varies per call), redaction, and the full three-scope resolution precedence.
- [x] Audit log service: immutable `AuditLog` model (actor, org, module, resource, before/after, IP, user agent, timestamp) + write helper used by mutation paths (FR-280, FR-282). Migration `20260810092004_audit_log`. Tenant-scoped like the FR-102 list requires, but with update/delete unconditionally rejected (`ImmutableRecordError`) in the scoping extension — even the `unsafeRunWithoutTenantScoping` bypass doesn't exempt it, immutability has no sanctioned exception in Phase 1. `organizationId`/`actorUserId` are plain columns with no FK/cascade, so the trail survives org or user deletion. `writeAuditLog()` in `packages/db/src/audit-log.ts` is the write helper. **Known gap:** immutability is only enforced on the `db` (extended) client — `prismaWithoutTenantScoping` (the raw client, exported for Super Admin/migrations/seeds) bypasses it entirely at the application layer; real hardening needs a DB-level privilege revoke or rule before production, not done here. 4 regression tests cover attribution, cross-org invisibility, and the update/delete rejection.
- [x] Super Admin portal shell (`web/src/app/super-admin/...`): organization list + detail, platform admin management, impersonation flow (time-boxed, banner-indicated, audit-logged) (FR-110–FR-113). Built after Phase 1B as planned, against the real auth/permission model — no placeholder auth. Layout gates on `core.platform.manage_organizations` via `requirePlatformAccess` (Next's `forbidden()`/`unauthorized()` boundaries, `experimental.authInterrupts` enabled). Organizations list/detail with suspend/reactivate/archive/schedule-deletion/cancel-deletion actions wired to the Phase 1A lifecycle service; a member row's "Impersonate" button calls the new impersonation service and redirects into the Tenant Admin portal as that user. Platform Admins page assigns/revokes `PlatformUserRole`s by email + role picker.
- [x] Tenant Admin portal shell (`web/src/app/tenant-admin/...`): org profile, user list/invite, team/workspace management, custom role builder UI (FR-120–FR-122). Layout requires an active org session (specific-permission checks live on individual mutating actions instead, per FR-153 — see the note below on that simplification) and shows the impersonation banner + "Stop impersonating" when `session.impersonatorUserId` is set (this, not the Super Admin layout, is where impersonation actually lands, since an impersonation session's `userId` is the *target* org admin). Pages: overview/profile (edit org name), members (invite via the new invites service, list, remove, manage pending invites), teams/workspaces (flat create/list/delete — no nesting UI), roles (create custom role, per-role permission checkboxes against the TENANT permission catalog, assign/unassign to members — the actual FR-122 "custom role builder"), sessions (FR-223's previously-deferred active-sessions UI: list/revoke, own current session marked).

Two real backend gaps surfaced while building the portals and got filled in `packages/db` first (with their own tests) before any UI touched them:
- **Impersonation** (`packages/db/src/auth/impersonation.ts`) — FR-112 had no service at all yet. Implemented as a special `Session` (new `impersonatorUserId` column + a much shorter `expiresAt`) rather than a separate mechanism, so the rest of the app just sees `userId` as the impersonated admin and works unmodified. `startImpersonation` checks the `core.platform.impersonate_organization_admin` permission and that the target is an active member of the org, then audit-logs the start; `endImpersonation` revokes the session and audit-logs the end. 4 regression tests.
- **Organization invites** (`packages/db/src/organization-invites.ts`, new `OrganizationInvite` model) — needed for "invite a user." Deliberately outside the tenant-scoping extension despite carrying `organizationId` — acceptance looks a row up by raw token alone, before any tenant context exists, same reasoning as `Session`/`VerificationToken`. Finds-or-creates the invitee's `User` row, activates their membership, applies a pre-assigned role if given. 4 regression tests.
- **Platform bootstrap** (`packages/db/src/auth/platform-bootstrap.ts`) — a real chicken-and-egg problem: nobody could ever reach the Super Admin portal without an existing Super Admin, and assigning one requires already being one. Resolved with an operator-controlled `SUPER_ADMIN_EMAIL` env var (added to `.env.example`/`packages/db/.env`) — whoever signs up with that email automatically gets a "Super Admin" `PlatformRole` holding every registered `PLATFORM`-scope permission, wired into `signUp()`. Idempotent, safe to leave set permanently. 3 regression tests.
- **Signup composes org creation** (`web/src/lib/auth/signup-flow.ts`) — `signUp()` (Phase 1B) deliberately only creates the user account; this is the one place that actually needs "a new organization signs up" as a single action (FR-130). Creates the user, the org (auto-slugified with collision retry), an active membership, and an "Owner" role holding every registered `TENANT` permission, then a session. 3 new tests in `web/src/lib/auth/__tests__/signup-flow.test.ts` (the only web-side test beyond the pre-existing pure resolver tests — everything else in the portals is thin page/action code calling already-tested `packages/db` services).

**Known simplifications, not full FR-153 enforcement on every page:** the Tenant Admin *layout* only requires an active org session, not a specific permission — granular permission checks (`requireOrganizationPermission`) live on each *mutating* Server Action instead (create role, invite member, update profile, etc.), which is where FR-153 actually bites; a member with zero admin permissions can currently still view these pages, just can't act on anything. Session revocation in the sessions page verifies ownership before revoking (a real check I added — `revokeSession()` itself doesn't verify ownership, callers must). Role deletion has no protection against deleting the "owner" role's last assignment (could lock an org out of its own admin — acceptable for Phase 1, worth hardening later).

## Phase 1B — Auth & sessions

- [x] Define `AuthProvider` adapter interface (methods every provider must implement). `packages/db/src/auth/provider.ts`: minimal `{ id, authenticate(credentials): Promise<{ userId }> }` — deliberately narrow (credential check only), so OAuth2/SAML/LDAP/social adapters (Phase 2+) implement the same shape without core auth flow (session creation, MFA, tenant context) caring which provider ran.
- [x] Implement Local provider: signup, login, password reset, email verification (FR-220). `packages/db/src/auth/local-provider.ts` + supporting modules: `password.ts` (Argon2id via `@node-rs/argon2`, OWASP m=19MiB/t=2/p=1 profile, not the library's lighter default; password minimum length is a platform setting — `security.min_password_length`, default 12 — not hardcoded), `verification-tokens.ts` (shared one-shot-token shape behind both email verification and password reset: random token, only its SHA-256 hash stored, consumed exactly once), `email-sender.ts` (a `console.log` placeholder — no notification framework exists yet, deferred per `ROADMAP.md`; swapping the implementation won't need call-site changes). `login()` compares against a precomputed dummy Argon2id hash when the email isn't registered, so response timing can't be used to enumerate accounts. Password reset revokes all existing sessions. **Deliberate scope boundary:** `signUp` creates only the User account, not an organization+membership — composing "a new org signs up" (user + org + membership together) is a route/workflow concern for whenever the actual signup page is built, not this adapter's job.

This round mirrors the just-completed OAuth adapter framework's shape exactly (registry + Settings-backed config + registry-driven Super Admin UI) and proves it with a real second provider: PayPal (Subscriptions API v1 + REST webhooks), per the brief's explicit scope (Razorpay/Paddle/Lemon Squeezy/Braintree/Authorize.Net/Square/bank-transfer/crypto all deliberately deferred — see below).

- [x] **Widened `PaymentProvider` contract** (`packages/db/src/billing/payment-provider.ts`): added `displayName`/`configFields`/`isConfigured()`, structurally identical to `OAuthAdapter` (`PaymentProviderConfigField` is its own type, not a shared import — kept independently evolvable, same reasoning platform-role/tenant-role RBAC stays structurally similar but textually separate). Also widened `verifyWebhookEvent` from synchronous to `Promise<ProviderWebhookEvent>` — a real, deliberate contract change, not free: Stripe's verification is a pure local HMAC check (no network call, unchanged behavior, only its call sites now `await`); PayPal's is not — PayPal's documented, supported verification path is a server-to-server call to `/v1/notifications/verify-webhook-signature`, with no published local-HMAC equivalent the way Stripe has one. A synchronous contract would have forced PayPal's adapter to lie about being synchronous, so the contract was widened instead of inventing a parallel async-only adapter shape (same principle `OAuthAuthorizeResult`'s optional `codeVerifier` already applies for PKCE vs non-PKCE). Full reasoning, including why `cancelSubscription`/`updateSubscription` were deliberately NOT added to the contract (this codebase's Subscription lifecycle is already provider-agnostic and neither adapter calls out to *initiate* a cancellation — adding an unused method would be speculative surface, not a real capability), lives in the file's header comment.
- [x] **Stripe updated to the widened contract with minimal internal changes** (`packages/db/src/billing/stripe-provider.ts`): `verifyWebhookEvent` became an `async function` around the exact same synchronous body; `createStripeProvider`'s returned object gained `displayName: "Stripe"`, `configFields: []`, and `isConfigured` (checks `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` are set). Every existing Stripe call site was touched only mechanically: `web/src/app/api/webhooks/stripe/route.ts` gained one `await`; `billing-stripe-provider.test.ts` and `billing-e2e.test.ts`'s `verifyWebhookEvent` assertions switched from `expect(() => ...).toThrow` to `await expect(...).rejects.toThrow`/`await provider.verifyWebhookEvent(...)`. No Stripe business logic changed — same "wrap the existing functions behind the new interface with minimal internal changes" tradeoff the brief explicitly sanctioned, and the same one the OAuth round took for the reverse case (Google/Apple left un-wrapped entirely).
  - **Stripe is deliberately NOT registered into the new payment-provider-registry.ts** — direct mirror of the OAuth round's Google/Apple decision. Stripe's config stays env-var-based (unchanged), so it has nothing for a registry-driven Settings config UI to render; wrapping it into the registry just to say it's "registered" would be cosmetic. It's a real, genuine `PaymentProvider` (implements the full widened contract, `isConfigured()` included) — just not a *registered* one. Only PayPal, the actually config-driven adapter, self-registers.
- [x] **Registry** (`packages/db/src/billing/payment-provider-registry.ts`): plain in-process `Map<id, PaymentProvider>` — `registerPaymentProviderAdapter`/`getPaymentProviderAdapter`/`listPaymentProviderAdapters` (+ test-only `unregisterPaymentProviderAdapter`, not exported from `index.ts`), line-for-line structural mirror of `oauth-registry.ts`. 5 regression tests against a dummy adapter (`payment-provider-registry.test.ts`), mirroring `oauth-registry.test.ts`'s exact cases.
- [x] **Settings-backed per-provider config** (`packages/db/src/billing/payment-provider-config.ts`) — the "reuse the Settings pattern, don't invent a new one" instruction taken literally: structural mirror of `oauth-provider-config.ts`, same `PlatformSetting` category convention (`payment_provider`, key `payment_provider.<adapter.id>.<field.key>`), same separate `enabled` kill-switch flag, same `hasRequiredPaymentProviderConfig`/`listPaymentProviderStatuses` shape driving a registry-based (not hardcoded) Super Admin UI. 7 regression tests (`payment-provider-config.test.ts`) against a throwaway dummy adapter id, mirroring `oauth-provider-config.test.ts`'s exact cases (round-trip, encryption, enabled default/toggle, required-vs-optional gating, full status aggregation).
- [x] **PayPal client** (`packages/db/src/billing/paypal-client.ts`) — a thin REST wrapper (OAuth2 client-credentials token fetch + a generic `request()` helper), not a full SDK: checked `packages/db/package.json`/`web/package.json` first, confirmed no PayPal SDK dependency exists, and PayPal's REST API is plain HTTP/JSON, so global `fetch` (Node ≥20, this repo's floor) was enough — no new dependency added, `pnpm-lock.yaml` untouched. `fetchImpl` is injectable purely for tests, mirroring `stripe-provider.ts`'s `options.client` injection, so the adapter's test suite never makes a real network call.
- [x] **PayPal adapter** (`packages/db/src/billing/paypal-provider.ts`), the concrete proof of the contract — genuinely different from Stripe's shape, not a reskin:
  - `createCheckoutSession` provisions a PayPal Product + Billing Plan lazily (PayPal Subscriptions, unlike Stripe Checkout Sessions, need both to exist before a Subscription can be created) on first checkout for a given platform `Plan.key`, then caches the PayPal plan id via the same Settings-backed config store every other per-adapter value uses (arbitrary keys, not a new mechanism) so a second checkout for the same plan skips re-provisioning — verified directly (a test asserts `/v1/catalogs/products`/`/v1/billing/plans` are each called exactly once across two checkout calls).
  - PayPal Subscriptions carry a single `custom_id` string (256 chars, no structured metadata object like Stripe's `metadata` bag) — both `organizationId` and our own `planKey` are packed into it (`orgId::planKey`) since PayPal's webhook payloads never expose our `planKey` any other way (they only know PayPal's own `plan_id`). A genuine per-provider difference the abstraction had to accommodate, not glossed over.
  - `verifyWebhookEvent` calls PayPal's real `/v1/notifications/verify-webhook-signature` endpoint. PayPal signs deliveries with FIVE headers (`paypal-transmission-id`/`-time`/`-cert-url`/`-auth-algo`/`-transmission-sig`), unlike Stripe's single `stripe-signature` — bundled into one JSON string via the exported `encodePayPalWebhookHeaders()` so they fit the shared contract's single `signatureHeader` parameter; the webhook route builds that string from the real request headers.
  - `handleWebhookEvent` mirrors `stripe-provider.ts`'s structure exactly (same `ProcessedWebhookEvent`-based idempotency guard, keyed `(provider: "paypal", providerEventId)`, then a `switch` on event type mapping to the same provider-agnostic `subscriptions.ts`/`invoices.ts` calls Stripe's handler uses): `BILLING.SUBSCRIPTION.ACTIVATED` creates/links a Subscription, `PAYMENT.SALE.COMPLETED`/`PAYMENT.CAPTURE.COMPLETED` renews it and records a paid Invoice, `BILLING.SUBSCRIPTION.SUSPENDED`/`RE-ACTIVATED`/`CANCELLED` pause/resume/terminate it. Organization resolution has a real fallback Stripe doesn't need: payment/capture resources don't carry `custom_id` (only the subscription resource does), so those events resolve org via `billing_agreement_id` looked up against our own `paypalSubscriptionId` link (set on `ACTIVATED`) instead — checked first, before falling back to treating `resource.id` as a subscription id, so a capture's own id is never mistaken for one.
  - Schema: `Subscription.paypalSubscriptionId`/`Invoice.paypalCaptureId` (`String? @unique`, migration `20260820090327_add_paypal_subscription_invoice_ids`) — one column per provider, matching the existing `stripeCustomerId`/`stripeSubscriptionId`/`stripeInvoiceId` convention rather than a generic `providerSubscriptionId`, since a real third provider (deferred) may not even have an equivalent single id. `invoices.ts`'s `CreateDraftInvoiceInput` gained `paypalCaptureId` alongside the existing `stripeInvoiceId`.
  - 20 regression tests (`billing-paypal-provider.test.ts`): registration, declared config fields, every `isConfigured()` gating combination (mirroring the Entra suite's cases), config-gated `createCheckoutSession`/`verifyWebhookEvent` throwing before any network call, spec-correct request shapes for Product/Plan/Subscription creation (asserted against real field names/nesting — `billing_cycles[0].frequency.interval_unit`, `pricing_scheme.fixed_price`, etc.) and the verify-webhook-signature call body, the Product/Plan caching behavior, malformed-header/malformed-body rejection, and the full `handleWebhookEvent` status-mapping + idempotency matrix (including the "no resolvable organizationId" case: the event is still recorded for idempotency but triggers no state change).
- [x] **New permission**: `core.platform.manage_payment_providers` (PLATFORM scope, `core-permissions.ts`) — mirrors `core.platform.manage_auth_providers`'s reasoning: enabling a payment provider is a distinct, more security-sensitive capability than generic platform settings. Registered via `pnpm --filter @saasclaude/db run seed` (19 core permissions now, up from 18).
- [x] **PayPal webhook route** (`web/src/app/api/webhooks/paypal/route.ts`) — structural mirror of the Stripe webhook route: reads the five `paypal-*` headers, 400s if any are missing, builds the JSON signature-header bundle, calls `paypalAdapter.verifyWebhookEvent`/`handleWebhookEvent`, maps `MissingPayPalConfigError`→500 and `PayPalInvalidWebhookSignatureError`→400. Deliberately not behind `withApiTenantContext`, same reasoning as the Stripe route: the signature itself is the credential, org resolves from the event after verification.
- [x] **Super Admin UI** (`web/src/app/super-admin/settings/payment-providers/{page,actions,provider-config-form}.tsx`, gated on the new permission, added to the sidebar under Settings next to Auth Providers): renders one card per adapter from `listPaymentProviderStatuses()` — not a hardcoded PayPal-specific form, direct structural mirror of `auth-providers/`. A future config-driven provider needs zero changes to this component. Confirmed via `pnpm build`'s route table: `/super-admin/settings/payment-providers` and `/api/webhooks/paypal` both listed.
- [x] **Invoice immutability preserved** — PayPal's `recordPaidCapture` (the PayPal equivalent of Stripe's `recordPaidInvoice`) goes through the exact same `createDraftInvoice` → `issueInvoice` → `markInvoicePaid` service-layer path Stripe uses; no direct writes to an already-issued `Invoice` row anywhere in this round, and corrections still only happen via `createCreditNote` (untouched). CLAUDE.md's invariant holds regardless of which provider processed the payment.
- [x] **Explicitly deferred, not attempted, per the brief**: Razorpay, Paddle, Lemon Squeezy, Braintree, Authorize.Net, Square, bank transfer, crypto (FR-211's full provider list) — PayPal alone was this round's scope, as the second data point proving the abstraction. Outbound `cancelSubscription`/`updateSubscription`-via-provider-API (initiating a cancellation *at* the provider, as opposed to reacting to one that already happened) — neither Stripe nor PayPal's adapter does this; nothing in Tenant Admin's billing UI calls out to cancel remotely for Stripe either, so this is a pre-existing gap, not a regression, and adding a speculative method to the contract for it was deliberately avoided (see the contract header comment).

## Notification-channel adapter framework + email/webhook/in-app (done)

REQUIREMENTS.md §2.14's notification framework was entirely unbuilt — the only prior email capability was `auth/email-sender.ts`'s `consoleEmailSender`, a documented `console.log` placeholder used by `local-provider.ts` (verification/reset) and `organization-invites.ts` (invites). This round builds the third instance of the same adapter-framework shape the last two rounds established (auth providers, payment providers) — contract + in-process registry + Settings-backed config + registry-driven Super Admin UI, gated on a new permission — and proves it with two real channels (email, webhook) plus a minimal in-app channel, wired to a generic notification-kind/template registry rather than hardcoded message copy.

- [x] **Channel contract** (`packages/db/src/notifications/channel.ts`): `NotificationChannel { id, displayName, configFields, isConfigured(), send(message) }`, structurally identical to `OAuthAdapter`/`PaymentProvider`. `send()` never throws — a channel reports `{ ok, error?, skipped? }` so one misbehaving channel can never abort dispatch to the others.
- [x] **Registry** (`notifications/channel-registry.ts`) — a plain in-process `Map`, line-for-line structural mirror of `oauth-registry.ts`/`payment-provider-registry.ts`. 5 regression tests (`notification-channel-registry.test.ts`), mirroring the other two registries' exact cases.
- [x] **Settings-backed per-channel config** (`notifications/channel-config.ts`) — direct structural mirror of `oauth-provider-config.ts`/`payment-provider-config.ts`: every field lands as a `PlatformSetting` row (category `notification_channel`), same encryption-at-rest + redaction-in-listings + separate `enabled` kill-switch as the other two frameworks. 7 regression tests (`notification-channel-config.test.ts`), mirroring the other two config suites' exact cases.
- [x] **Notification-kind/template registry** (`notifications/notification-kind-registry.ts`, new `NotificationKind` model, migration `notifications_framework`) — a *data* registry (unlike the code-level channel registry above), direct structural mirror of `permission-registry.ts`/`billing/resource-types.ts`: `registerNotificationKinds()` idempotently upserts by key, `NotificationKindKeyConflictError` on a cross-module claim. ## Phase 2, round: sessions/invites/notifications over REST + SDK-drift CI (done)

Closes two of round 2's explicit follow-ups (TASKS.md line 176's round) rather than picking a fresh ROADMAP.md item: the remaining tenant-scoped resources that already have real `packages/db` services but no `/api/v1` route, and wiring `packages/api-client`'s `pnpm run generate` into CI so a spec/generated-schema drift actually fails a build instead of relying on a human remembering to regenerate.

- [x] **Real design decision, made before writing any route, not assumed from the brief**: the brief's framing ("self-service listing of the *calling user's* own sessions/notifications") doesn't fit this API surface's actual auth model. `ApiKey` has no `userId` — it's an organization-level credential with no calling-user concept at all (confirmed by reading `api-keys.ts`'s own schema comment: "an API key has no User/UserRole to resolve permissions through"), unlike the cookie-authenticated Tenant Admin settings pages the brief's wording was implicitly modeled on. Redesigned both resources as **organization-scoped, not self-scoped**: `GET /sessions`/`GET /notifications` list what's active/present *within the calling organization* (optionally narrowed with `?userId=` to one member), the same shape `GET /members` already uses for "the org's roster," not "my own." ## Cross-file test-isolation flakiness — actually fixed (done)

Picked up from the "Next" note above rather than deferred a third time. Root-caused, not just re-flagged: the flakiness had two genuinely distinct sources, both stemming from the same underlying gap (this repo's test strategy uses a real shared local/CI Postgres with no per-test transaction isolation, and nothing serialized every process that touches it).

- [x] **Root cause #1 (the one actually reproduced and named in every prior flare-up)**: `web/vitest.config.mts` had no `fileParallelism` setting (Vitest's default is `true`) — unlike `packages/db/vitest.config.mts`, which has run with `fileParallelism: false` since Phase 1A/1B (`b4e8da0`). Every prior incident that named specific colliding files (`signup-flow.test.ts` racing `api/v1/__tests__/roles.test.ts`) was two files *within the `web` package itself* running concurrently and racing the shared, non-tenant-scoped `Permission` catalog table (one enumerates-then-grants every TENANT permission, others create-then-delete their own scoped test rows). `packages/db`'s own suite was never actually the source of this specific race — it already had the guard; `web` was the one package that didn't.
- [x] **Root cause #2 (the resource-contention timeouts, a separate mechanism)**: `turbo.json`'s `test` task only `dependsOn: ["^build"]` (upstream *build*, not upstream *test*) — nothing stopped `@saasclaude/db#test` and `web#test` from being scheduled as two concurrent OS processes by turbo, each opening its own pool of connections against the same Postgres instance. That's consistent with the previously-flagged timeouts in unrelated-looking `packages/db` tests (`notification-webhook-channel.test.ts`'s real `node:http` server, `notification-channel-config.test.ts`, `auth-impersonation.test.ts`) during a full `pnpm test` run — load/contention from a second, simultaneously-running DB-heavy test process, not a logic bug in those files.
- [x] **Fix, mirroring the pattern this codebase already trusted rather than inventing a new mechanism**: `web/vitest.config.mts` gained the identical `fileParallelism: false` `packages/db` already carries (closes root cause #1). `turbo.json` gained a `"web#test": { "dependsOn": ["^build", "@saasclaude/db#test"] }` override (closes root cause #2) — `web`'s test task now only starts after `@saasclaude/db`'s test task has fully finished, so the two DB-touching suites never run as concurrent processes. `@saasclaude/api-client#test` (no DB, mocked `fetch` only) was deliberately left on the default, unserialized `test` task — it has nothing to race.
- [x] **Verified the fix actually holds, not just that it typechecks**: ran the full suite via `pnpm exec turbo run test --force` (bypassing turbo's cache so every run is a genuine fresh execution against the real local Postgres/Redis) three times in a row — 327 `packages/db` + 114 `web` + 3 `api-client` tests, 444 total, all green on every run, zero flakes. Previously this same full-suite run had reproduced a real failure roughly 1 in 3 attempts per the prior rounds' notes; three consecutive clean forced runs is a real, not coincidental, signal the fix holds.
- [x] **Full verification**: `pnpm typecheck`/`lint`/`test`/`build` all pass from the repo root. One unrelated environmental snag hit and cleared along the way, same as several prior rounds: a stale `.next/dev/types` (Next's generated route-type ambient declarations, left over from before this session's edits) produced nonsense TS syntax errors on `web#typecheck` — cleared `web/.next` and ran a full `pnpm build` to regenerate it cleanly before re-typechecking; not a real code issue, and not related to the turbo/vitest config changes above.
